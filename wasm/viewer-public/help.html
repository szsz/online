COOL WASM Viewer — help & integration guide

Collabora Online running entirely in the browser over WebAssembly. No LibreOffice server, no WOPI host — the viewer sideloads a ~265 MB WASM editor into an iframe, then keeps it warm for instant document switches. This page explains the moving parts and how to embed them.

Try it now

Two viewer modes are available. Click a doc in the file list to open it.

Co-editing viewer → Single-user viewer →

First load is slow. The first time you open a document the browser downloads ~57 MB brotli (≈265 MB raw) of WASM plus ~16 MB brotli (≈94 MB raw) of LibreOffice resources. A Service Worker caches these, so subsequent loads are near-instant.

Locally the three run behind wasm/launch-sni-router.sh, which terminates TLS on :443 and routes by SNI to each service's own port (:6934 / :6932 / :9091). On Azure they are three App Services, fronted by Azure's own TLS.

Document storage

Files are content-addressed (SHA-256). The viewer maintains two indexes: _meta/<url-encoded-name>.json maps a display name to its current {hash, size, updatedAt}, and _blobs/<hash> stores the immutable bytes. Two storage backends ship:

  • Local filesystem (STORAGE_BACKEND=local) — LOCAL_STORAGE_DIR on disk. Used for dev.
  • Azure Blob (STORAGE_BACKEND=azure) — authenticated via account key or full-container SAS URL (DOC_STORAGE_SAS_URL). Used for the Azure deploy.

Late joiners download the checkpoint directly from the viewer's /api/blobs/<hash> endpoint, which never lies about bytes (the hash is the URL), so there is no risk of desync between what the relay promised and what the blob endpoint delivers.

Modes: single-user vs co-editing

The editor is the same WASM binary either way — the difference is whether a relay WebSocket is attached.

Co-editing mode default

The page at / loads the editor with ?relay=wss://<relay-host>/. The embedded relay-adapter.js intercepts every user-input message, routes it through the relay (which assigns a sequence number), and applies only the relay-ordered stream to the local editor. All peers apply the same sequence, so all replicas stay byte-identical. Use this for any document you want to share.

Single-user mode

The page at /singleuser.html loads the editor without the relay=… parameter. relay-adapter.js detects this and short-circuits to local mode: no WebSocket, no sequence numbers, but the save/hash-tracking bits still run so conflict detection works if someone else edits the file via a different client. Use this when you're the only editor and want to skip the relay round-trip.

Integration guide — embedding the editor in your own page

The editor is a plain iframe pointing at cool.html. The only coupling to the wrapper page is a small set of URL params and a postMessage protocol. To put the editor in your own page:

1. Cross-origin isolation

The WASM threads use SharedArrayBuffer, which requires the top-level page to be cross-origin isolated. Your page must send: 

Cross-Origin-Opener-Policy:   same-origin
Cross-Origin-Embedder-Policy: require-corp
Permissions-Policy:           cross-origin-isolated=(self "<editor-origin>"),
                              clipboard-read=(self "<editor-origin>"),
                              clipboard-write=(self "<editor-origin>")

Every subresource the top-level page loads must carry Cross-Origin-Resource-Policy: cross-origin (or be same-origin). The editor already does this — your wrapper code must as well.

2. The iframe URL

<iframe
  id="editor-frame"
  src="<editor-origin>/browser/cool.html
        ?WOPISrc=<url-encoded-doc-name>
        &access_token=test
        &relay=wss%3A%2F%2F<relay-host>"
  allow="cross-origin-isolated; clipboard-read; clipboard-write">
</iframe>
  • WOPISrc — document identifier. For our viewer this is just the file name (report.docx). The editor uses it as the room id and as the key for /api/files/<name>.
  • access_token — any non-empty string works for our viewer (no auth beyond the SAS/secret on the backend). A real WOPI host would put a signed bearer token here.
  • relay — WebSocket URL to the relay. Omit to enable single-user mode.

3. Upload the doc to /wasm/<name>

Before the iframe's WASM calls fopen("/tempdoc") (≈3–6 s into init), the doc bytes must be reachable at <editor-origin>/wasm/<name>. Your wrapper can either push them up with fetch(POST) or rely on the viewer's built-in click handler if you're just embedding the viewer UI. Example: 

await fetch(editorOrigin + '/wasm/' + encodeURIComponent(name), {
  method: 'POST',
  body: docBytes,   // Blob, ArrayBuffer, or Uint8Array
});

The editor serves GET /wasm/<name> back to the WASM later; it's a short-lived transient store, not a canonical place to keep files.

4. postMessage protocol

The wrapper talks to the iframe with postMessage. The useful messages (see wasm/relay-adapter.js for the full list):

DirectionMessageIdPurpose
iframe → parentApp_LoadingStatusFires Document_Loaded / Initialized — drop your loading shield here.
iframe → parentRelayActivatedRelay joined + replay done. User can now type.
iframe → parentWasmDocReady, WasmSwitchVisibleFirst-paint / hot-switch visible. Wrapper drops any switch overlay.
iframe → parentKeyRequestClient asks for an encryption key for a (fileId, keyVersion). Wrapper fetches from /api/keys/<fileId>/<keyVer> and posts KeyResponse back.
parent → iframeRelaySwitchRoomAsk an already-warm editor to hot-switch to a different doc (same or compatible type). Bypasses the cold reload.
parent → iframeRelayDisconnect / ForceSaveClean teardown, or override a save conflict.

5. Hot-switch vs cold-reload

Opening a document of the same type as the current one (writer→writer, calc→calc, impress→impress) can be done with RelaySwitchRoom — the WASM runtime stays mounted, a new doc is pushed in, and the user sees the swap in well under a second. Opening a document of a different type (writer→calc) is a cold reload: the iframe's src is replaced and the WASM re-instantiates (~5–10 s thanks to HTTP cache + Service Worker).

6. Style boundaries

The editor iframe carries its own CSS. Don't try to reach into it — COOL's style is not a public API. What is stable is the postMessage protocol, URL params, and the three service endpoints documented above.

Running the stack locally

# Deploy the editor bundle into /tmp/static-deploy/public/
bash wasm/deploy.sh

# Start the four services (all read wasm/.env)
node wasm/message-relay.js &
bash wasm/launch-viewer.sh &
sudo bash wasm/launch-editor-static.sh &
sudo bash wasm/launch-sni-router.sh &

The SNI router needs :443 (hence sudo). Relay + viewer + editor-static each have their own HTTPS cert under /etc/letsencrypt/live/.

Running on Azure

bash wasm/deploy-azure.sh deploys all three apps into the same resource group. Config lives in wasm/.env.deploy: 

RESOURCE_GROUP=Szilveszter-coediting
APP_SERVICE_PLAN=szebeni-wasm-plan
VIEWER_APP_NAME=szebeni-wasm-viewer
RELAY_APP_NAME=szebeni-wasm-relay
EDITOR_APP_NAME=szebeni-wasm-static
DOC_STORAGE_ACCOUNT=wopiteststorage
DOC_STORAGE_KEY=…
DOC_STORAGE_CONTAINER=documents
VIEWER_EXTRA_ORIGINS=https://files.atgpartners.info
EDITOR_EXTRA_ORIGINS=https://files.atgpartners.info

The first editor deploy is slow (~15 min — brotli -q 11 of 265 MB online.wasm is CPU-bound). Subsequent deploys reuse the cached .br when the source bytes haven't changed.
