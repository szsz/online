COOL WASM Viewer — help & integration guide

Collabora Online running entirely in the browser over WebAssembly. No LibreOffice server, no WOPI host — the viewer sideloads a ~265 MB WASM editor into an iframe, snapshots its initialised heap to Cache Storage, and warm-restores it on return visits for fast second opens. Documents are end-to-end encrypted (the secret lives in the URL fragment; the server only ever sees opaque ciphertext). This page explains the moving parts and how to embed them.

Try it now

Two viewer modes are available. Click a doc in the file list to open it.

Co-editing viewer → Single-user viewer →

First load is slow. The first time you open a document the browser downloads ~57 MB brotli (≈265 MB raw) of WASM plus ~16 MB brotli (≈94 MB raw) of LibreOffice resources. A Service Worker (/browser/sw.js) puts these in Cache Storage, and a snapshot of the initialised WASM heap is stashed under the wasm-snapshot cache, so the second visit warm-restores in well under 5 s instead of paying the full cold init.

Document storage and v2 encryption

Every uploaded document is encrypted client-side under a fresh 128-bit secret. The secret never leaves the browser — it lives in the URL fragment (#file=<22-char-base64url>) and is cached in localStorage.rf_v1 so the sidebar can render plaintext display names. The server only ever sees opaque bytes addressed by an opaque fileId (HKDF derivation of the secret).

  • Key derivation: HKDF-SHA256 on the 16-byte secret → contentKey (32 B AES), nameKey (32 B AES), fileIdBytes (32 B → 64-char hex fileId).
  • Ciphertext layout: 12 B random IV + AES-256-GCM ciphertext + 16 B tag. The filename is separately encrypted under nameKey and stored as encName.
  • Storage: ciphertext + encName are written to /api/v2/file/<fileId>. The file manager performs all encryption — neither the editor nor the relay ever sees the key.
  • Open flow: the viewer fetches the ciphertext, decrypts client-side, POSTs the plaintext to /wasm/<fileId> on the editor, then spawns the iframe with WOPISrc=<fileId>.
  • Save-back: Ctrl+S has the editor postMessage the plaintext bytes to the viewer (WasmFileSave); the viewer encrypts and PUTs to /api/v2/file/<fileId>, then reports a hash + locator back to the editor for the relay's next checkpoint.

Two storage backends ship:

  • Local filesystem (STORAGE_BACKEND=local) — LOCAL_STORAGE_DIR on disk. Used for dev.
  • Azure Blob (STORAGE_BACKEND=azure) — authenticated via account key or full-container SAS URL (DOC_STORAGE_SAS_URL). Used for the Azure deploy.

Bytes are also exposed at /api/blobs/<hash> for the late-join checkpoint flow: the hash is the URL, so a content-addressed download cannot disagree with the relay's recorded checkpoint hash. Plaintext v2 files use /api/v2/file/<fileId> as the locator instead — every late joiner re-decrypts client-side.

Sharing a doc. Send the URL including the fragment (the #file=… part). Without the fragment, the recipient lands on an empty sidebar — the server cannot supply the secret. Bookmarking the page works because the browser keeps the fragment.

Modes: single-user vs co-editing

The editor is the same WASM binary either way — the difference is whether a relay WebSocket is attached.

Co-editing mode default

The page at / loads the editor with ?relay=wss://<relay-host>/room/<encoded-room-key>. The embedded relay-adapter.js intercepts every user-input message (keys, mouse-button events, UNO commands), routes it through the relay (which assigns a monotonic sequence number and fans out to every peer in the room, sender included), and only then applies the broadcast to the local Kit. All peers apply the same sequence, so all replicas stay byte-identical. Mouse-move is the one exception — it goes straight to the local Kit and is buffered, with the last buffered move flushed to the relay just before the next click so remote cursors land at the right spot without flooding the WebSocket. Use this for any document you want to share.

Single-user mode

/singleuser.html redirects to /index.html?singleuser. The viewer detects the flag and builds the iframe URL without the relay=… parameter, so relay-adapter.js short-circuits to local mode: no WebSocket, no sequence numbers, but Ctrl+S still encrypts and stores the plaintext to /api/v2/file/<fileId>. Conflict detection (hash mismatch on save) still runs. Use this when you're the only editor and want to skip the relay round-trip.

Warm restore (snapshot)

After the first document successfully paints, the editor serialises its WASM HEAPU8 + a small metadata blob into the wasm-snapshot Cache Storage. Subsequent visits skip the cold init: the heap is restored before callMain(), the C++ side resumes from a self-parked safe point, and a fresh switchdocument opens the target file. Real-world warm opens land at ~5–11 s (cold can be 25–40 s on a fresh browser).

  • Default: ON.
  • Opt out for a session: append ?planc=0 to the viewer URL. The flag is propagated to the iframe and the cached snapshot is purged.
  • Snapshots carry a build fingerprint injected by deploy.sh; a stale snapshot from a prior deploy is silently discarded and the visit falls back to cold.

Hot-switching between documents

When the user clicks a different file in the sidebar, the viewer decides between two paths:

  • Same doc-type (writer→writer, calc→calc, impress→impress) — the iframe stays mounted. The viewer posts RelaySwitchRoom to detach the old room, rewrites the iframe's hash to #switchdoc=<fileId>, and the editor calls switchdocument against the new bytes already staged at /wasm/<fileId>. End to end ≈ 1 s.
  • Cross doc-type (writer↔calc, calc↔impress, etc.) — cold reload. The iframe's src is replaced; the warm snapshot still gets us to a running runtime in < 5 s, then the new document loads on top. (A pure same-process cross-type hot-switch is tracked but not enabled — sectionContainer tear-down is incomplete.)

Integration guide — embedding the editor in your own page

The editor is a plain iframe pointing at cool.html. The only coupling to the wrapper page is a small set of URL params and a postMessage protocol. To put the editor in your own page:

1. Cross-origin isolation

The WASM threads use SharedArrayBuffer, which requires the top-level page to be cross-origin isolated. Your page must send: 

Cross-Origin-Opener-Policy:   same-origin
Cross-Origin-Embedder-Policy: require-corp
Permissions-Policy:           cross-origin-isolated=(self "<editor-origin>"),
                              clipboard-read=(self "<editor-origin>"),
                              clipboard-write=(self "<editor-origin>")

Every subresource the top-level page loads must carry Cross-Origin-Resource-Policy: cross-origin (or be same-origin). The editor already does this — your wrapper code must as well.

2. The iframe URL

<iframe
  id="editor-frame"
  src="<editor-origin>/browser/cool.html
        ?WOPISrc=<fileId-or-name>
        &access_token=test
        &relay=wss%3A%2F%2F<relay-host>%2Froom%2F<encoded-room-key>
        &fileStorageUrl=https%3A%2F%2F<viewer-origin>
        &UserName=<display-name>
        &displayName=<plaintext-title>"
  allow="cross-origin-isolated; clipboard-read; clipboard-write"
  referrerpolicy="no-referrer">
</iframe>
  • WOPISrc — document identifier. For v2 this is the 64-char hex fileId; for legacy plaintext use the file name. The editor uses it as the room id and as the path under /wasm/.
  • access_token — any non-empty string works for our viewer (no auth beyond the SAS/secret on the backend). A real WOPI host would put a signed bearer token here.
  • relay — WebSocket URL including /room/<encoded-key>. Omit to enable single-user mode.
  • fileStorageUrl — the viewer origin. The editor cannot infer it (referrer is suppressed and the parent origin is cross-origin); it is needed so save-back posts hit the right /api/v2/file/<fileId>.
  • UserName — short pronounceable nickname shown on remote cursors.
  • displayName — optional plaintext title shown in the editor chrome (the opaque fileId is otherwise what the editor would render).
  • planc=0 — opt out of the warm-restore snapshot for this session (cold-only). Omit to keep warm restore on.

3. Stage the doc bytes at /wasm/<fileId>

Before the iframe's WASM calls fopen("/tempdoc") (≈3–6 s into init), the plaintext doc bytes must be reachable at <editor-origin>/wasm/<fileId>. The viewer decrypts a v2 file client-side and POSTs the plaintext there before swapping the iframe src. If you're embedding the editor yourself, do the same: 

await fetch(editorOrigin + '/wasm/' + encodeURIComponent(fileId), {
  method: 'POST',
  body: plaintextBytes,   // Blob, ArrayBuffer, or Uint8Array
  mode: 'cors',
});

The editor serves GET /wasm/<fileId> back to the WASM later; it's a short-lived transient store, not a canonical place to keep files. The editor never sees the encryption key.

4. postMessage protocol

The wrapper talks to the iframe with postMessage. The useful messages (see wasm/relay-adapter.js for the full list):

DirectionMessageIdPurpose
iframe → parentApp_LoadingStatusFires Document_Loaded / Initialized — early hint, but don't drop the shield on it alone.
iframe → parentWasmProgressLive percentage / label / detail from wasm-loader.js. Drives the shield's progress bar.
iframe → parentWasmPrewarmReadyEditor finished prewarm with a blank doc and is ready for a same-type hot-switch.
iframe → parentWasmDocReady, WasmSwitchVisibleFirst canvas paint / hot-switch visible. Combined with RelayActivated the wrapper can drop the shield.
iframe → parentRelayActivating / RelayActivatedLate-join replay started / completed. Until RelayActivated, user keystrokes are dropped on the floor.
iframe → parentRelayLateJoinPhaseCoarse-grained progress for the late-join checkpoint download + replay.
iframe → parentWasmFileSaveEditor hands plaintext bytes to the wrapper for v2 encryption + PUT to /api/v2/file/<fileId>. Wrapper replies with WasmFileSaveResult carrying {ok, hash, locator}.
iframe → parentSaveComplete / SaveConflictOutcome of a Ctrl+S round-trip. Conflict means another client wrote since the last open; the wrapper can offer a ForceSave.
iframe → parentKeyRequestClient asks for a relay-message-encryption key for a (fileId, keyVersion). Wrapper fetches from /api/keys/<fileId>/<keyVer> and posts KeyResponse back.
parent → iframeRelaySwitchRoomAsk an already-warm editor to hot-switch to a different doc of the same type. The wrapper then sets iframe.src's hash to #switchdoc=<fileId>.
parent → iframeRelayDisconnect / ForceSaveClean teardown of the relay socket, or override a save conflict.

5. Style boundaries

The editor iframe carries its own CSS. Don't try to reach into it — COOL's style is not a public API. What is stable is the postMessage protocol, URL params, and the three service endpoints documented above.

Relay protocol — pointer

The relay speaks a small binary protocol over a single WebSocket per client. Frames are [type(1)] [viewId(4 BE)] [payload…]; broadcast frames carry an extra [seq(4 BE)] assigned by the server. Implemented frame types: 0x00 user message, 0x02 announce join, 0x03 announce leave, 0x04 join request, 0x05 join response (with optional checkpoint + cursor map for late joiners), 0x06 join-ready / register, 0x07 save-rotation, 0x0A mismatch redirect. Reserved-but-ignored: 0x01, 0x09. The full lifecycle (empty room, late join, parked joiner, checkpoint rotation on Ctrl+S) is spelled out in wasm/CO-EDITING-ARCHITECTURE.md.

Running the stack locally

# Deploy the editor bundle into /tmp/static-deploy/public/
bash wasm/deploy.sh

# Start the four services (each reads wasm/.env via its launch wrapper)
bash      wasm/launch-relay.sh         &
bash      wasm/launch-viewer.sh        &
sudo bash wasm/launch-editor-static.sh &
sudo bash wasm/launch-sni-router.sh    &

The SNI router needs :443 (hence sudo). Relay, viewer, and editor-static each have their own HTTPS cert under /etc/letsencrypt/live/, configured in wasm/.env via namespaced keys (RELAY_SSL_CERT, EDITOR_SSL_CERT; the viewer uses bare SSL_CERT/PORT). deploy.sh always restarts the relay last so no client stays on a mismatched WS protocol.

The first editor deploy is slow (~15 min — brotli -q 11 of 265 MB online.wasm is CPU-bound). Subsequent deploys reuse the cached .br when the source bytes haven't changed.
